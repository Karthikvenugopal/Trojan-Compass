# Graph integration and contract mismatches

## Current graph boundary

The adapter implements the async `GraphRepository` from `trojan_compass.recommendations.graph`. That is the typed read model Peri's recommendation engine currently consumes. The Neo4j adapter uses `asyncio.to_thread` around blocking driver operations, parameterized Cypher, and no request-result cache. The fake implements the same methods for deterministic tests. The read API supports destination resolution, scoped requirements, interest-to-destination suggestions through explicit `HAS_REQUIREMENT → ABOUT → Topic` evidence, action retrieval by skills/topics, and exact course lookup.

Karthik's current API boundary is separate: `ChatService` builds the v2 `RecommendationRequest(context=RetrievalContext, user_query=...)`, invokes an injected `RecommendationService`, then validates a v2 `RecommendationResult`. Production composition calls `create_app(extractor=..., recommendations=..., mode="production")`. The GraphRepository is injected into the recommendation service, not directly into `create_app`.

## Mismatches to resolve before composing branches

1. **Recommendation request version:** the current default branch's `trojan_compass.contracts.RecommendationRequest` contains `context: RetrievalContext`. The current `feat/recommendation-engine` implementation imports `StudentProfile` and reads `request.profile`. Those types and fields do not exist in the default branch's v2 contracts. Peri needs to rebase/adapt the service to v2 before it can satisfy the `RecommendationService` passed to Karthik's `create_app`.
2. **Graph boundary version:** the earlier graph proposal in this branch used synchronous `resolve_destinations`/`scoped_requirements`/`find_actions` methods and local dataclasses. Those are replaced here with Peri's actual async protocol and Pydantic graph models. Any caller built against the old names or return values must update.
3. **Requirement labels:** ingestion records `required`/`preferred`; Peri's `Requirement.importance` uses `core`/`preferred`. The adapter maps `required → core` and `preferred → preferred`. Confirm that Peri intends `core` to carry the required-requirement semantics before relying on it for explanations or ranking.
4. **Date precision:** campus occurrences may publish dates without start/end times. The ingestion layer preserves those dates in `EventOccurrence` attributes. Peri's `EventInfo` accepts only offset-aware datetimes, so the adapter leaves `start`/`end` unset for date-only records rather than inventing times. Add date-only schedule fields to the shared graph/API contracts if the UI needs machine-readable date ranges.
5. **Relationship evidence excerpts:** Neo4j preserves excerpts on `Evidence` nodes and relationship properties. `Requirement.statement` carries a requirement excerpt to Peri, but `CampusAction.sources` and Karthik's shared `Source` contract expose only URL, title and checked timestamp. Action excerpts therefore do not cross the recommendation boundary today; add an evidence field to the shared graph model if downstream explanations need the exact excerpt.
6. **Networking semantics:** Peri's `SkillLink.relation` supports `networking`, while this graph's event network activity is represented as an evidenced `Topic` (for example, Career networking). No networking skill edge is created without explicit skill evidence. Keep that distinction when integrating or expanding event data.

7. **Prerequisite semantics:** ingestion requires every `HAS_PREREQUISITE` edge to distinguish `formal` from `helpful`; Peri's `Prerequisite` model has no corresponding type field, and the current graph read methods do not return prerequisites. The graph retains the distinction, but the recommendation contract cannot currently explain or filter on it.
8. **Featured organizations:** the graph accepts `FEATURES` only with explicit source evidence, but `CampusAction` has no company/team feature field and the read adapter does not expose those edges. The current consumers cannot show an event's evidenced company or team participants.
9. **Occurrence schedule and status:** Karthik's `EventSchedule` and Peri's `EventInfo` use offset-aware datetimes. The import format accepts date-only occurrence dates, and the recommendation models do not represent a date-only range. Occurrence status is returned when the occurrence is retrieved; event occurrence dates are preserved in storage but omitted from the consumer model. Add date-only schedule fields to the shared contracts before exposing these dates.
10. **Scoped requirement subjects:** ingestion can attach requirements to Skill or Topic, but Peri's `Requirement` read model contains only a `SkillNode`. The adapter currently returns skill requirements; topic requirements remain stored and evidenced but unavailable as scoped requirements.

The campus seed has no company/team features or destination-wide action relevance edges. Interest-based directions only use an explicit requirement-about-topic path; no action is connected to every career destination. Course offerings remain unknown when no source lists an offering. Exact course lookup resolves course identities (including their linked learning edges), not a fabricated catalog of dated section offerings.

## Privacy and operational boundary

`RetrievalContext` is temporary. Graph calls may receive request-derived names/interests/skill IDs to retrieve shared facts, but those parameters are not cached or logged. Never persist them, add `Student` nodes, log Cypher parameter values, or attach them to traces. Neo4j server-side query, audit, APM and managed-service logs still require deployment-level redaction/retention controls described in [DATA_IMPORT.md](DATA_IMPORT.md).
